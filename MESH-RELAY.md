# CORE INVENTORY — Offline ESP-NOW mesh relay

Lets a laptop with no internet still get its inventory changes to the cloud
backend, by relaying them through a mesh of ESP32 boards until one reaches a
laptop that *does* have internet.

## The story

Each laptop running the CORE INVENTORY web app is paired one-to-one with an
ESP32, tethered over USB. When `storageService.ts` fails to reach the
backend directly (offline, or the simulated-offline toggle in Settings), it
hands the queued mutation to its paired ESP32 instead of just leaving it
stuck in the local queue.

That ESP32 floods the mutation across an ESP-NOW mesh of every other ESP32
in range. Each node that receives it forwards it to its *own* paired laptop,
which checks whether **it** has internet. The first laptop that does have
internet applies the mutation to the backend on the original laptop's
behalf, and a confirmation travels back through the mesh to the node that
originated it — which tells its own laptop the mutation is synced.

Every ESP32 runs both directions at once (origin **and** relay) rather than
a manually switched mode, since any node may need to do both at the same
time: inject its own laptop's offline work into the mesh, and forward
someone else's flood through to its own laptop.

## Protocol

Two framing layers, both defined once in
[`firmware/esp32-relay/include/protocol.h`](firmware/esp32-relay/include/protocol.h)
and mirrored by hand in `espRelayService.ts` (no shared build step between
C++ and TypeScript, so keep both in sync if you change either).

### USB serial (laptop ↔ its own ESP32)

Serial is a raw byte stream with no built-in message boundaries, so frames
are explicitly delimited: `MAGIC(1) TYPE(1) LEN_LO(1) LEN_HI(1) PAYLOAD(LEN
bytes) CHECKSUM(1)`, one frame per message (no fragmenting needed the way
the old BLE link required, since a serial write isn't MTU-limited the same
way). The checksum is a cheap sum-of-bytes integrity check; a mismatch drops
the frame and resyncs on the next magic byte rather than getting stuck -
useful since this same USB-CDC channel also carries the firmware's plain-text
debug logging, which could in principle land a stray byte mid-frame. Four
message types:

- `OUTBOUND_MUTATION` (laptop → ESP32): `{ localId, action, payload }` — "relay this, I'm offline."
- `INBOUND_REQUEST` (ESP32 → laptop): `{ relayToken, action, payload }` — "the mesh needs an internet check for this."
- `INBOUND_RESULT` (laptop → ESP32): `{ relayToken, ok }` — sent only on success; failures are silent so the mesh keeps trying other nodes.
- `SYNCED_ACK` (ESP32 → laptop): `{ localId, ok }` — "your mutation reached the backend."

### ESP-NOW (ESP32 ↔ ESP32)

A binary `MeshFrame` struct (~222 bytes, under ESP-NOW's 250-byte payload
cap) fragmented/reassembled per message. Key fields: an 8-byte `msgId`
generated by the *origin* node, the origin's MAC, a hop-count `ttl`
(default 8), and fragment index/total.

- **Flooding**: every node broadcasts to `FF:FF:FF:FF:FF:FF`. A dedupe table
  (`msgId` + `fragIndex`, last 64 seen) stops a node from rebroadcasting the
  same fragment twice, which is what makes the flood terminate instead of
  looping.
- **Reverse-path ack routing**: each node remembers, per `msgId`, which
  neighbour it *first* heard that message from (`rememberParent`). A
  `RELAY_ACK` retraces that path hop-by-hop back to the origin instead of
  being flooded a second time. If a node's parent entry has expired, it
  falls back to a best-effort flood of the ack.
- **No mesh configuration required**: nodes don't need to know each other's
  MAC addresses ahead of time — only the broadcast address is a static peer.
  All nodes must share one fixed WiFi channel (`MESH_WIFI_CHANNEL` in
  `main.cpp`) since ESP-NOW has no channel negotiation.

## History: why this moved from Bluetooth to USB

The laptop↔ESP32 hop was originally Web Bluetooth (BLE GATT). On real
hardware this turned out to be a deep, recurring source of instability from
combining a BLE GATT server with ESP-NOW on the ESP32's single 2.4GHz radio:

- Enabling the BT controller after WiFi/ESP-NOW was already active aborted
  inside the WiFi/BT coexistence arbiter (`coex_core_enable`) instead of
  failing gracefully - fixed by reordering init to bring BLE up first.
- The coexistence arbiter separately required WiFi modem sleep to stay
  *on* whenever both radios were active, the opposite of what's normally
  best for ESP-NOW latency.
- Even with both of those fixed, one board still failed `esp_now_init()`
  outright on some boots - most likely the BLE/Bluedroid stack's own
  runtime heap usage leaving too little free heap for WiFi to complete its
  own init, though this was never fully root-caused since moving off BLE
  removed the problem entirely.
- Windows/Chrome-side GATT connections were separately flaky (stale
  OS-level pairing state, "GATT Server is disconnected" errors) independent
  of the firmware issues above.

USB serial removes the Bluetooth radio from the picture entirely, so none of
the above applies - the tradeoff is a laptop must stay physically tethered
to its own ESP32 rather than just nearby.

## Known limitations

- **Best-effort, not guaranteed delivery.** If no node in the mesh has
  internet, a relayed mutation simply sits until the origin laptop itself
  regains a connection (same as today's baseline behavior) — there's no
  persistent retry beyond the TTL-bounded flood.
- **A mutation is still bounded by the ESP-NOW mesh hop's own size cap**
  (`MESH_MAX_FRAGMENTS * MESH_DATA_MAX` in `protocol.h`, a few KB), since
  every relayed mutation has to cross at least one ESP32-to-ESP32 hop
  regardless of how much more USB itself could carry. `espRelayService.ts`
  splits an oversized `STOCK_CHECK` payload into several independently
  relayed chunks to work within that, at the cost of each chunk being
  acked/retried separately rather than atomically as one mutation.
- **`STOCK_CHECK` relay always applies to inventory.** The frontend's only
  call site (`handleReconcileStock` in `src/App.tsx`) always passes
  `applyToInventory: true`, so the relay endpoint hardcodes that too — see
  the comment in `relay_mutation()` in `database/app.py`.
